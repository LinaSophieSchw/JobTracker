## Ablauf

Diese Story hat keinen Klick im Browser. Sie legt das Fundament für die
Fahrzeitberechnung (US 30001).

```
Frontend    (nichts in dieser Story)
Backend     wohnadresse_lesen()            src/app/datenbank.py
Datenbank   Tabelle benutzer, Demo-Benutzer mit id 1
```

### 1. Tabelle `benutzer` mit drei Adressspalten anlegen

[`src/app/datenbank.py`, Zeilen 48–59](../../../src/app/datenbank.py#L48-L59),
Funktion `tabellen_erstellen()`:

```python
verbindung.execute("""
    CREATE TABLE IF NOT EXISTS benutzer (
        id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
        name VARCHAR(100) NOT NULL
            CHECK (length(trim(name)) > 0),
        wohnadresse_strasse VARCHAR(200),
        wohnadresse_postleitzahl VARCHAR(20),
        wohnadresse_ort VARCHAR(200),
        erstellt_am TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
        geaendert_am TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
    )
""")
```

- `IF NOT EXISTS`: Die Tabelle wird nur angelegt, wenn sie fehlt.
- Die Wohnadresse steht in drei Spalten statt in einem langen Text
  ([ADR 0009](../../decisions/0009-adresse-in-drei-feldern.md)).

### 2. Demo-Benutzer einfügen

[`src/app/datenbank.py`, Zeilen 64–74](../../../src/app/datenbank.py#L64-L74):

```python
verbindung.execute(
    """
    INSERT INTO benutzer (
        id, name, wohnadresse_strasse,
        wohnadresse_postleitzahl, wohnadresse_ort
    )
    VALUES (%s, %s, %s, %s, %s)
    ON CONFLICT (id) DO NOTHING
    """,
    (1, "Demo-Benutzer", "Bundesplatz 3", "3005", "Bern"),
)
```

- `ON CONFLICT (id) DO NOTHING`: Gibt es den Benutzer mit id 1 schon,
  passiert nichts. Wiederholtes Ausführen erzeugt keinen zweiten Benutzer.
- Bundesplatz 3, Bern ist eine öffentliche Adresse ohne Bezug zu einer realen
  Person.

### 4. Wohnadresse aus der Datenbank lesen (neu)

[`src/app/datenbank.py`, Zeilen 134–160](../../../src/app/datenbank.py#L134-L160):

```python
def wohnadresse_lesen(datenbank_url):
    """Liefert die Wohnadresse des aktuellen Benutzers in drei Teilen.

    Gibt None zurück, wenn kein Benutzer gefunden wird.
    """
    with verbindung_oeffnen(datenbank_url) as verbindung:
        ergebnis = verbindung.execute(
            """
            SELECT wohnadresse_strasse, wohnadresse_postleitzahl, wohnadresse_ort
            FROM benutzer
            WHERE id = %s
            """,
            (aktuelle_benutzer_id(),),
        ).fetchone()

    if ergebnis is None:
        return None

    return {
        "strasse": ergebnis[0],
        "postleitzahl": ergebnis[1],
        "ort": ergebnis[2],
    }
```

1. **Fragen:** `SELECT` holt die drei Adressteile des Benutzers mit id 1.
2. **Prüfen:** `fetchone()` liefert `None`, wenn keine Zeile passt. Dann gibt
   auch die Funktion `None` zurück, statt mit `ergebnis[0]` abzustürzen.
3. **Umpacken:** Aus `("Bundesplatz 3", "3005", "Bern")` wird ein Dictionary.
   Später steht im Code `wohnadresse["ort"]` statt `wohnadresse[2]`.

### 5. Ausblick: Verwendung in US 30001

Die Wohnadresse ist der **Startpunkt**, die Arbeitsadresse aus dem Formular das
**Ziel**. Skizze, noch nicht umgesetzt:

```python
wohnadresse = wohnadresse_lesen(datenbank_url)       # woher, aus der Datenbank
arbeitsadresse = formulardaten                       # wohin, aus dem Formular
fahrzeit = fahrzeit_berechnen(wohnadresse, arbeitsadresse)
```

## Knackpunkt

**Die Wohnadresse steht nicht im Formular, sondern nur in der Datenbank.** Die
Fahrzeitberechnung braucht aber beide Adressen. Gelöst mit der eigenen kleinen
Funktion `wohnadresse_lesen()`:

- einzeln testbar,
- wiederverwendbar in US 30001 (erstes Speichern) und US 30003 (erneutes
  Speichern),
- liest aus der Datenbank, statt die Adresse fest in den Berechnungscode zu
  schreiben. Eine spätere Profilseite funktioniert so ohne Umbau der
  Berechnung.

**Zusammenarbeit im Team:** Lina hat die Tabelle `benutzer` parallel gleich
umgebaut (PR #16). Beim Zusammenführen entstand ein Merge-Konflikt in
`tabellen_erstellen()`. Weil beide Versionen inhaltlich gleich waren, wurde
Linas Version übernommen; dazu kam nur `wohnadresse_lesen()`.

## Mögliche Fragen der Dozierenden

**«Warum ist die Postleitzahl ein Text und keine Zahl?»**

```sql
wohnadresse_postleitzahl VARCHAR(20),
```

Mit einer Postleitzahl rechnet man nie. Eine Zahl würde ausserdem führende
Nullen verschlucken, wie es sie in anderen Ländern gibt (z. B. 01067 Dresden).
Text speichert sie genau so, wie sie geschrieben wird.

**«Was prüft dein Test, wenn er gar keine echte Datenbank verwendet?»**

```python
verbindung.execute.return_value.fetchone.return_value = (
    "Bundesplatz 3", "3005", "Bern",
)
```

Der Mock ist eine nachgebaute Datenbank: Er merkt sich, was unser Code an
`execute()` übergibt, und gibt eine vorbereitete Antwort zurück. So prüft der
Test unsere Logik (richtige id, richtiges Umpacken ins Dictionary) schnell und
ohne Internet. Ob das SQL selbst stimmt, wurde einmal von Hand mit der echten
Datenbank geprüft.

**Zusatzfrage: «Wozu sind die `%s` im SQL?»**

```python
"""
SELECT wohnadresse_strasse, wohnadresse_postleitzahl, wohnadresse_ort
FROM benutzer
WHERE id = %s
""",
(aktuelle_benutzer_id(),),
```

Das sind Platzhalter. Die Werte werden separat übergeben und nie direkt in den
SQL-Text eingesetzt. Das schützt vor SQL-Injection, bei der jemand SQL-Befehle
in ein Eingabefeld schreibt.

**Zusatzfrage: «Warum entsteht beim Neustart kein zweiter Benutzer?»**

```sql
ON CONFLICT (id) DO NOTHING
```

`tabellen_erstellen()` ist so geschrieben, dass man sie beliebig oft ausführen
kann (idempotent): `IF NOT EXISTS` überspringt vorhandene Tabellen,
`ON CONFLICT (id) DO NOTHING` überspringt den vorhandenen Benutzer.
